- A webhook endpoint whose deliveries fail **without interruption** for at least 24 hours is now disabled with `disabled_reason` `auto-disabled after sustained delivery failures`, which completes the third and last published auto-disable case (`3xx` landed earlier, the private-address rule before it). The published trigger is the *duration* of uninterrupted failure rather than a delivery count, and a single `2xx` resets the window, so the streak is persisted (`webhooks.failing_since`, migration 044) rather than counted in a process — a counter would reset on every restart and the rule would never fire in the deployment it exists for — and a successful delivery writes the reset, so failures interrupted by any success never accumulate toward a disable. Re-enabling an endpoint clears the streak, so a recovered endpoint starts a fresh window instead of being disabled again by its next failure. The attempt that triggers the disable is terminal, like the other two cases. **The 24-hour window is a local parameter, not a published value**: the contract states the trigger's shape and never its length, so the number is chosen long enough that an ordinary outage cannot reach it and is recorded as a local choice rather than as conformance.

### Changed

- A webhook delivery whose endpoint host is an internal name (`localhost`, `.local`, `.internal`, …) or resolves to a private address is now refused **before any connection**, with the endpoint disabled and `disabled_reason` set to the published `auto-disabled: endpoint URL resolved to an invalid address`. That is the second of the three published auto-disable cases, and like the `3xx` case the attempt is terminal rather than retried, and the reason is cleared when an operator re-enables the endpoint. The screening reuses the shared classifier that already guards `web_fetch` (`src/core/web/address-policy.ts`), so a hex-spelled IPv4-mapped private address cannot slip past the dotted one, and a resolver answer that mixes public and private addresses is refused rather than raced. **It is off by default and turned on per deployment with `MANAGED_AGENTS_WEBHOOK_SCREEN_PRIVATE_ADDRESSES`**, which is a recorded deviation from the published rule: the published case is unconditional, but loopback *is* a private address, this runtime is local-first, and its receiver normally shares the host — every webhook test in this repository delivers to a loopback listener — so enforcing it by default would disable the receiver a self-hosted deployment exists to talk to. A deployment exposed to untrusted callers turns it on; with it on, same-host delivery no longer works, which is what the switch means.

- A webhook endpoint that answers a `3xx` is now **disabled** with the published machine-readable reason `auto-disabled: endpoint URL returned a redirect (3xx)` (`disabled_reason`, migration 043), and that delivery is terminal: no retry is scheduled, so it never appears in the retry-due pass. The published contract states a response that triggers auto-disable is never retried, while the three-attempt ceiling still applies to every other failure, which a control test pins. Previously the redirect was already never followed (`redirect: 'manual'`), but the response was classified only as `2xx` or not, so a `3xx` looked exactly like a `500` and was retried three times. The rule is about the response rather than the attempt number, so a *retry* that observes a redirect disables the endpoint too — reachable when an operator re-enables an endpoint while a retry is still due. `disabled_reason` is reported only while the endpoint is disabled and is cleared when `PUT /v1/webhooks/{id}` re-enables it, so an active endpoint never advertises a resolved reason. This was the first of the three published auto-disable cases to be implemented; the other two landed in the two changes above, and the deviations that remain for webhook delivery are recorded in `contracts/anthropic-cma/operations.md`.
- `PUT /v1/webhooks/{id}` accepts the published `status` field (`active` / `disabled`), which is the enable/disable surface for a subscription. The column was already stored, already projected by `toWebhook`, and already honoured by the dispatcher — which selects `status = 'active'` for both first attempts and retries — but **no route wrote it**, so an endpoint that was ever disabled could only be brought back by editing the database by hand. This lands before the published automatic-disable rules deliberately: implementing those first would have turned an endpoint that retries forever today into one that is permanently dead, while the published contract states all three automatic cases are reversible by re-enabling the endpoint. An unrecognised value is refused by name rather than ignored, because a silently ignored status reads as a successful re-enable on an endpoint that never comes back; omitting the field leaves the stored value unchanged, like every other field in that partial update, so a rename cannot silently re-enable an endpoint an operator switched off.

- `GET /v1/sessions/{id}/artifacts` now answers the published collection envelope `{data, prev_page, next_page}` instead of `{data, has_more, first_id, last_id}`. It was the last canonical `/v1` collection on the local shape, so with this change every canonical collection serves the envelope the published contract uses — a claim `contracts/anthropic-cma/pagination.md` can now make without naming an exception, and which the capability matrix's pagination entry previously overstated. Both cursors are `null` because the listing returns its complete set unwindowed: a caller reading `next_page` finds an honest "no more pages" rather than no field at all. Windowing this listing remains a separate change, and the tests pin that the conversion did not start cutting pages. The SDK's `artifacts()` return type follows the route. Row order within a second is still unspecified — `created_at` is `datetime('now')` and this query has no tie-break — which reorders an unwindowed page but cannot drop a row from it, so the tests assert set equality rather than an order they cannot honestly claim.

- `GET /v1/sessions/{id}/events` now answers the published collection envelope `{data, prev_page, next_page}` instead of `{data, has_more, first_id, last_id}`. Three of those four field names occur **nowhere** in the published contract — a search of the published documentation finds zero occurrences of `has_more` and `first_id` against 34 of `next_page` — so a client built against the published contract read `next_page` from this listing, found nothing, and could not page at all: the listing cut its page at `limit` and reported the cut in a vocabulary the caller does not speak. `next_page` is now a followable cursor carrying `{order, filter: {session_id}, after_id}`, which is what `contracts/anthropic-cma/pagination.md` had already described this route as doing; `prev_page` is always `null` because the scan is forward-only and an invented predecessor would not resolve. The local `after_id` and `limit` are unchanged. A `page` the route cannot have issued — malformed, issued for a different session, replayed under a different ordering, or naming an event that is not in the log — is a `400` rather than a silent restart from the first event, because a restart is answered as though it were the page after the caller's position and the caller cannot detect it. The SDK's `events()` return type and its accepted options follow the route. The one canonical `/v1` collection still on the local envelope is `/v1/sessions/{id}/artifacts`, filed separately so each conversion is verified on its own.

- Implements the published `limit`/`page` window on the vault and memory-store listings, closing the gap those two listings had recorded as an open difference. The published rule is "使用 `limit`（默认 20，最大 100）和 `page` 游标进行分页" (`管理智能体上下文/Dreams.md:575`), and both listings read neither parameter: each answered one unfiltered page with `prev_page`/`next_page` both `null`, so a caller who followed the documented `next_page` had nothing to follow and a caller who asked for page two was handed page one again with no indication the request had been ignored. The reading lives in `src/api/routes/query-params.ts` and both collections call it for the same reason `include_archived` does — a rule this specific kept in two places is two places for the accepted values to drift, and the test compares the two collections' refusals to each other rather than each to a literal. The cursor is opaque and carries the ordering **and** the `include_archived` view that produced the page; replaying one under the other view, or against the other collection, is a `400` rather than an answer to a page that never existed for that query. A `limit` outside `1..100`, a non-integer, or a repeated value is a `400` naming the accepted range instead of falling back to the default: a caller who asked for 500 rows and received 100, or asked for `abc` and received the default, has been answered as though they asked for something else. Two things had to be measured rather than assumed. `created_at` is `datetime('now')`, so rows created in the same second share a timestamp and the listing's ordering was not total — a windowed listing has to slice a total order or a page boundary can repeat or drop a row, so both listings now order by `created_at DESC, rowid DESC`, which is insertion-recency within the tie group. And adopting the published default of 20 **truncates** what the local Console sees, because it reads one page through `getCursorPage` and does not follow `next_page`; its two call sites now ask for `?limit=100`, which is the convention its session call already used (`apps/console/src/hooks/useConsoleData.ts`), with the remaining 100-row ceiling recorded as the Console's own limit rather than the endpoint's. Tests drive both listings over a real listener and a real SQLite file and close every walk by checking the pages partition the collection exactly once, since a page that repeats or skips a row still has the right length. Docs updated in `docs/api.md`, `contracts/anthropic-cma/credentials.md` and `contracts/anthropic-cma/memory-stores.md`.

- Treats an unreadable directory as a listing failure rather than an empty listing, which fixes every commit-pinned `github_repository` resource mounting zero files. `listFilesRecursive` caught the `readdir` failure and returned `[]`, so its promise resolved for **every** path — including one that does not exist. The materializer decides cache reuse with `listFiles(cachePath).then(() => true).catch(() => false)`, so that made every cache probe a hit: a `commit`-pinned repository took the cached branch, never ran `git clone`, and mounted nothing while reporting `cached: true`. The mount succeeded, the session started, and the agent simply had no repository — the worst shape for this failure, because nothing downstream had an error to report. Only a `commit` checkout is affected (`githubCacheKey` returns `undefined` for a branch or tag, so a branch always clones), which is why it survived: the branch path, the common one, worked. `listFiles` now propagates the error, honoring the contract the call site already stated in its own `.catch`. The same rule applies one layer down, where a staging directory that cannot be listed is now an error instead of a silently partial mount. That the defect was invisible to the existing suite is the more useful finding: the materializer tests fake `listFiles` with a fake that throws `ENOENT` for a path the test did not plant, and its comment says "a listing either succeeds or it does not" — the intended contract, encoded only in the fake, which production then violated while every test passed. The new tests therefore use the production `listFiles`, `readFile`, and `removeDir` over a real temporary cache root and fake only git, so a clone produces real files on disk and the real listing has to find them. Recorded in `contracts/anthropic-cma/github-repository.md`.

- Records a created session's `resources` as durable resource instances, so the documented session-resource surface is reachable for a session the runtime created. `POST /v1/sessions` accepted `resources`, echoed them back, and stored them in the session's own column, but created **no** instances — measured against a live listener at `e8c021bc`, a session created with a `github_repository` resource answered `201` while `GET /v1/sessions/{id}/resources` answered `200 {"data": []}` and `session_resource_instances` held no row. The column is the declaration the sandbox mounts; the resource API addresses *instances*, each with its own `sesrsc_` id, and that distinction is load-bearing — a file resource is added and removed while a session runs, and a GitHub resource's id is what a token rotation addresses. So the whole group was unreachable for every session that had ever been created: `GET`/`PATCH`/`DELETE /v1/sessions/{id}/resources/{rid}` had no id to accept, and a client following the documentation could not address a resource it had just declared. The instances are attached in `SessionManager.create` rather than in each route, because only two of the four creation paths can use `createWithInitialEvents`: `POST /v1/runs` with `response_mode: 'sse'` or the default `'wait'` creates the session and streams the reply itself, so it cannot hand the events over, and a per-route hook is precisely what left the table empty — `attachSessionResources` was imported by nothing but its own unit test. Attaching in `create` means every path gets it, including ones added later, and it puts the instances inside the caller's transaction when there is one: a rejected `initial_events` batch now discards the resource instances it attached along with the row and the events, which the existing transaction tests assert unchanged through the same `attachResources` seam. `memory_store` still attaches only at creation, and the instances are created with `atCreation: true`, so the type the contract reserves for session creation is not accidentally made live-addable. Five behaviours are pinned over a real HTTP listener: the created instance is addressable by its own id on the single-resource route; `POST /v1/runs` attaches for the session it creates; plain `create` attaches, which is the path the streaming run modes use and the one a per-route hook could not reach; detaching removes the instance while the session's declaration survives, which is what proves the listing is backed by a table rather than projected from the session's JSON column; and a `memory_store` attaches at creation while the same type through the live add route is still refused. Docs updated in `docs/api.md`.

- Exposes the published error envelope's `type` and `code` on `ManagedAgentsApiError`, closing the client half of the error taxonomy. The envelope is structural — `{"error":{"type":"invalid_request_error","code":"invalid_agent_ref","message":"..."}}` — and a caller is meant to branch on it, but the SDK read only `error.message`, so the runtime's entire taxonomy was unreachable and a caller wanting to tell a wrong agent reference from a malformed body had to substring-match English prose that is not a stable interface. `error.type` and `error.code` now carry the runtime's own values, which makes a future rewording of a message safe rather than a silent breaking change for a consumer that was forced to match on it — the code that the previous change had to print as prose (`model.api_key: TYPO is not set`) is now readable as a value. The message is deliberately **unchanged** (`API error 400: agent must be a standard agent id`), so this is additive for anyone already matching on it. The error body is also now read exactly once: the previous implementation called `res.json()` and then `res.text()` on the same `Response`, whose body is single-use, so the non-JSON fallback could never succeed — a non-JSON failure was reported as `statusText` rather than as the body the runtime actually sent, and the fallback was dead code that looked alive. `requestText`, which backs artifact and file content plus metrics, goes through the same reader, so a JSON envelope is no longer reported as raw JSON text with no fields readable.

- Registers the documented `managed-agents settings` group and moves the SDK's canonical runtime settings helpers onto the routes they claim to call. The group is documented as covered in `docs/api-matrix.md:86` — "Get, set model boundary, and validate canonical runtime settings" — and ticked in `docs/spec/tasks.md:144`, and its three commands are implemented in `src/cli/runtime-management-commands.ts`, the module the previous change registered only halfway: these are the commands it deliberately left unregistered rather than register broken (**#466**). Measured against a live listener, `settings get` threw `Cannot read properties of undefined (reading 'metadata')`, `settings validate` threw `result.checks is not iterable`, and `settings set-model` failed with `API error 404: No route matches this request`. The first two read a document taken from a type no route produces — the runtime's internal registry report, with `model_provider`, `loop_engine.implemented`, `storage.metadata.type` and `validation.checks` — so every field a reader could reach for was `undefined` at runtime while type-checking; the third sent `PATCH /v1/x/settings`, where the route mounts `PUT`. `settings.patch()` is therefore a read-merge-write: it reads the current `revision` and `saved_config`, merges the partial document over it, validates the result, and writes it with the revision it read, so a masked secret survives the round trip and a concurrent writer is refused with `409` rather than silently overwritten — there is no automatic retry, because the SDK cannot know whether re-applying the patch is still meaningful. A document the runtime would reject throws `RuntimeSettingsValidationError` before the write, naming each failing field, including the environment variable behind a `${NAME}` reference that does not resolve in the **runtime's** environment; that detail is precisely what the shared error path drops (**#464**), and without it `settings set-model --api-key-env TYPO` would report only `Settings configuration is invalid`. The SDK's `RuntimeSettingsSummary` and `RuntimeSettingsPatch` now describe the routes' own fields, secrets are documented as surviving the round trip because reads mask a stored key as `********` and the store treats that sentinel as "keep", and an integration test drives a real HTTP listener through a recording `fetch` that delegates to it rather than replacing it, so the verb asserted is the verb served.

A message is queued on the session's serialized execution chain and starts a turn, so routing a steer through it would apply the instruction only after the turn it was meant to influence had ended — the runtime would then have reported a delivery that changed nothing. The event is therefore never turned into a `user.message`: it carries `input_id`, `text`, and an optional `expected_turn_id`, and it is written to the live engine session's own input channel, never to the execution chain, so it can carry text to a running turn and nothing else — it cannot start work, expose a tool, or change the tool policy the child was launched with. The answer carries a receipt the caller can act on: `delivered`, `duplicate` (the same `input_id` with the same text, which the engine is not told twice), `conflict` (the same `input_id` with different text, refused rather than merged into the earlier steer), `rejected` (no live session was accepting steering, so resending is safe), or `outcome_unknown` (the write was not acknowledged and must never be replayed, because the child may already have acted on it). `accepted` is `false` for `rejected` and `conflict` only, since reporting an unacknowledged write as a failure would invite exactly the replay the contract forbids. Admission is fail-closed rather than queued: at most one steer is in flight per turn, a steer arriving with no turn in flight or for a child that is gone is refused rather than buffered for a later turn, an `input_id` already spent on other text is refused, and `expected_turn_id` must name the active turn when it is present. Steer admission closes before the turn's `turn_complete` is published and receipts already accepted settle before it, so a turn completion cannot overtake a steer it still owes an answer to. The receipt is persisted in the event's `metadata` (`input_id`, `steer_state`, and `turn_id` / `detail` when present) so a client reading the log back learns what the engine actually did, the SDK exposes the same call as `sessions.steer(id, { inputId, text, expectedTurnId? })`, and a malformed steer is refused with `400 invalid_request` naming the field rather than recorded.

- Lets an operator preauthorize a gated Pi tool decision once. A gated native tool call had exactly one way to be answered — a person's `user.tool_confirmation` — so an unattended session stopped dead at the first `always_ask` call. `loop_engine.options.approval_mode` now selects the second way: `interactive` (the default, and the resolution for an omitted key) keeps waiting for a person exactly as before, while `preauthorized_once` lets the runtime answer the call itself under the platform-owned rule that mode installs. The decision travels the same one-shot path a person's does — the conditional consume on the durable `pi_tool_interactions` row is still the only thing that authorizes execution — and it is recorded with `decision_source: "platform"` and published as `requires_confirmation: false` with `confirmation_source: "platform"`, so no client can read an automatic decision as a click by a person and the session never reports `requires_action` for it. Nothing about the mode is standing or widening: the next gated call is decided again, the mode is read per gate so turning it off is honored by the following decision while a decision already recorded keeps its source, the compiled `--tools`/`--exclude-tools` plan and the gated name list are untouched, a call the rule does not name keeps waiting for a person rather than being denied unattended, and every path that cannot consume a trustworthy decision still denies. - Serves the CMA contract matrix from `GET /v1/x/capabilities` under `contract`, beside the existing runtime tool inventory. The matrix records, for every published contract area, whether this build implements the behaviour, the reason for any other status, and the contract document that carries the detail, so the served inventory and the published contract cannot drift apart silently. The addition is additive: `type` and `capabilities` keep their existing shape and status codes.

- Adds path-addressed session memory mounts. A session can mount up to eight stores at whole-segment paths; file tools persist mounted content through `memory_records`, read-only mounts reject writes, shell access is refused while mounts are attached, and existing-file updates require a content precondition.

- Records an immutable version row per memory write. A memory is overwritten in place, so previously nothing could say what a path held before, attribute a change to the session that made it, or notice that two writers raced on the same path. Every create, update, and delete now records the store, the memory, a per-memory monotonic version number, the path, the content, its SHA-256, its size in bytes, the change kind, and the session that made it, and a unique index refuses a second writer claiming a version that already exists rather than letting it overwrite the first. `GET /v1/memory_stores/{id}/memory_versions` lists a store's recorded versions newest first, optionally scoped to one memory, and `GET /v1/memory_stores/{id}/memory_versions/{versionId}` reads one by its own id.
- Attaches a resource to a session as a per-session instance with its own `sesrsc_` id, so it can be listed, read, updated, and detached without rewriting the session payload. Attachment is additive and reversible: detaching a resource from one session leaves it attached to every other session that holds it, and a session can hold more than one resource of the same type at its own position. The session row, its initial events, and its resource instances are written in one transaction, so a failure part-way through leaves neither a session that claims a resource it does not hold nor an orphaned resource row. A `memory_store` resource can only be attached at session creation, because memories are part of the context the session was built with. A github_repository `authorization_token` stays write-only and is never echoed in any response; rotating it is the only updatable field, and changing the repository, checkout, or mount path requires a new instance.
- Governs an MCP tool by its toolset's permission policy instead of letting it fall through to `always_allow`. The toolset kind supplies the default when nothing is configured — `always_ask` for an `mcp_toolset`, `always_allow` for the built-in toolset — and an explicit per-tool or toolset-wide policy overrides it in both directions. A tool the server exposed but the agent never named is governed by the same default rather than by nothing: it is admitted, it keeps no `execute` until the caller approves it, and it is listed for the strategy so the confirmation list and the resolved tool map cannot disagree. A tool the operator marked `never_allow` is not admitted at all rather than shipped and gated, because shipping it invites the model to call something the operator forbade. The runtime naming rule now lives in one dependency-free module so the permission layer reuses it instead of carrying a second copy that used a prefix the runtime never produces.
- Closes the custom tool loop. A custom tool is exposed to the model with its description and input schema and no local `execute`, a call to it is persisted as an `agent.custom_tool_use` event that parks the session in `requires_action`, and the caller answers with `user.custom_tool_result` naming the `custom_tool_use_id` — after which the turn resumes with that result as the model-facing tool result. The runtime never executes a custom tool and never fabricates a result for one. A result naming a call that is not pending, and a second result for a call that already has one, are each refused before they are appended, so a caller cannot inject an answer into a session or answer a call twice.
- Accepts a custom tool either as a canonical `custom` entry in `tools[]` or in the legacy `custom_toolset` grouping, and projects one canonical shape on every agent response. The canonical entry carries `name`, `description`, and `input_schema`, with `parameters` still accepted as a legacy alias. A tool the legacy grouping disables is dropped rather than translated into a policy, and a canonical entry carrying a `permission_policy` is refused because the caller executes the tool and decides whether to run it, so a policy field would claim governance the runtime does not hold. A name that collides with a built-in tool, a name declared twice across both shapes, and a malformed input schema are each refused with a message naming the offending entry. `getCustomToolNames`, `getCustomToolConfigs`, `canonicalToConfig`, and `findCustomToolConfig` report the same tool set for both wire shapes.

- Spills an oversized tool result into the sandbox and gives the model a short

- Lets a session event stream opt into token-level previews with a repeated

- Adds `POST /v1/runs`, which starts one turn and returns its result without

- Exposes `GET /v1/x/capabilities` as the canonical inventory for locally
  executable built-in tools. Agent create/update and session creation now

- Prices model consumption and enforces a session spending ceiling. `POST /v1/sessions` accepts an optional `budget` (`{type: "limit", max_list_cost: {amount, currency: "USD"}}`, where `amount` is an integer number of cents written as a string), it is stored in a new nullable `sessions.budget` column, and the session echoes it back. Cost is computed from the session's own `span.model_request_end` records into integer microcents, so the ceiling comparison never depends on float rounding, and the reported `list_cost` is that total rounded up so a client is never told it spent less than it did. Once the spend reaches the ceiling, the next event that would start model work is refused with `budget_reached` and only events that settle work already in flight are accepted, so the next model request does not start. Prices come from an operator-supplied profile (`MANAGED_AGENTS_COST_PROFILE`) rather than vendor list prices: a model with no entry has no list price, a budgeted session naming one is refused with `budget_model_without_list_price` rather than metered against an invented rate, and `usage.list_cost` is omitted while any used model is unpriced instead of being reported as a partial total. `session.usage` now also carries the session's `budget` (or `null`) and zeroed `server_tool_use` counters. A budget is attachable at creation only, cannot be raised to a value at or below what the session already consumed, and cannot be re-added after removal; `session.usage`/the session payload keep "never had a budget" and "had one removed" distinguishable. The capability matrix entry moves from `planned` to `partial`.

- Exports a session as a replayable handoff bundle. `POST /v1/x/sessions/{id}/handoff-bundle` packages one session as recorded evidence and stores it, `GET /v1/x/handoff-bundles` lists stored bundles newest first, and `GET /v1/x/handoff-bundles/{id}` returns a stored payload unchanged. The package uses three open standards rather than bespoke formats: RO-Crate 1.1 for the description graph, BagIt (RFC 8493) for sha512 integrity manifests with a manifest self-digest, and an in-toto statement in a DSSE envelope signed with an Ed25519 key derived from the runtime secret key material — a local trust root that proves origin and integrity, not authorship. Message bodies and file bytes are excluded by default, and each excluded body is replaced by a byte count and sha256 reference, so prompt text and file contents leave the runtime only when the caller asks for them. Credential secrets never enter a bundle: denied and injected credentials are recorded as metadata only, and any transcript key naming a secret is replaced with `[redacted]` and reported in `redaction.scrubbed_fields`. `replay.mode` is `recorded_replay`, with tools never re-executed and model requests never re-issued, while `resume` and `fresh_run` are declared unsupported rather than implied. Bundles are stored immutably in a new `handoff_bundles` table (migration M036).

- Accepts, validates and persists a scheduled deployment's `timezone`. The field was documented and the cron engine already evaluated an expression in a zone, but nothing could set one: the request body was not read, no column held it, and every schedule therefore ran in UTC. Both `POST` and `PUT /v1/scheduled-deployments` now read the cadence from either the flat `cron` and `timezone` fields or the canonical `schedule: { type: "cron", expression, timezone }` object, refuse an unknown IANA name with `400` without writing a row, default to `UTC` when the field is omitted, and echo the stored zone on every response. `next_run_at` is computed in the resolved zone, and an update that moves the cadence re-arms it in the new zone unless the caller supplies its own `next_run_at`. The column is added by migration M037 as `NOT NULL DEFAULT 'UTC'`, so a schedule written before it existed keeps running on the same instant it did.

### Changed
- An interrupted tool call now reports that its external outcome is **unknown** instead of suggesting a retry. When the process dies mid-turn, or a turn fails before the tool returned, the runtime appends a placeholder `tool_result` so the message sequence stays paired. That placeholder read `(interrupted by server restart — retry if needed)`, which is an instruction to do the one thing that must not be done: for a call that already wrote a file, sent an HTTP request or ran a shell command, it asserts the effect probably did not happen and invites a second one. The runtime knows exactly one thing in this situation — that no `tool_result` was recorded — and cannot know whether the call took effect, so the message now says the outcome is unknown (`Tool call was interrupted before its result was recorded; its external outcome is unknown. It may or may not have taken effect.`). The text is one exported constant (`INTERRUPTED_TOOL_OUTCOME_MESSAGE` in `src/core/session/session-recovery.ts`), beside the function that defines what an orphan is. The two call sites previously carried **different sentences for the same epistemic situation** — the crash path the one above, and the failed-session resume path `(previous turn failed before this tool returned)` — so the message stopped being a parameter: both paths now record the constant, which is what keeps them from drifting apart again. The record is still `is_error: true` and still pairs with its `tool_use`; what changed is the claim it makes. Tool calls are still not retried, and a crashed *model* call is still not recovered — saying the outcome is unknown is what makes a later retry decision correct rather than blind, so classification is deliberately a separate change. Only runtime-executed tools reach this path (`OrphanedToolUse.resultType` covers `agent.tool_result` and `agent.mcp_tool_result`), so the statement is always about a call that was actually dispatched — a custom tool is executed by the client and is never described this way.
- Publishes `deployment_run.started`, `deployment_run.succeeded` and `deployment_run.failed`, so a subscription learns that a timed run happened and how it ended. All three were accepted in a subscription and could never fire, so a receiver could not tell "no run has come due yet" from "this runtime has no run events". The published table describes them as one mechanism, not three: `.succeeded` and `.failed` carry `data.id`, the **run** id, and it states that this is the same id as that run's `.started` event — so the id linkage is an invariant spanning all three names, and implementing a subset would ship a correlation the contract promises and the runtime could not honour. That is why they are one change. The run id is `data.id`, the id of the `scheduled_deployment_runs` row, and therefore the id `GET /v1/deployment_runs/{id}` accepts. `succeeded` is raised for a row with status `created_session` and `failed` for `failed`, exclusively — a failed run never also reports success. **Only a timed run raises them.** The manual route `POST /v1/deployments/{id}/run` shares `runSchedule` with the timed path, and it takes a **caller-supplied** `trigger_type` (`stringField(body.value.trigger_type) ?? 'manual'`), so the published rule could not be written as `triggerType === 'scheduled'`: a manual run would have declared itself timed and emitted into a rule that excludes it. The rule lives on the path instead — publication is in `runDueScheduledDeployments`, which only the background tick and `POST /v1/deployments/run-due` reach — so a manual run publishes nothing whatever it calls itself. `deployment_run.started` is published once the run is **recorded**, before its outcome rather than at the instant it begins: `runSchedule` is synchronous and writes its row in a single terminal statement, so there is no in-progress state for `started` to point at, and the published handler contract tells a receiver to fetch the resource by `data.id` — publishing earlier would send that fetch to a `404` for a run that had genuinely started. The event is late rather than false, and a test measures resolvability **inside the receiver** so the claim is checked rather than asserted; adding a persisted in-progress run state is a change to the run status vocabulary, not to this event, and is not part of this change. Delivery stays best-effort: publication is attempted per run, and a subscriber that cannot be reached never stops a due deployment from running or abandons the rest of the pass — asserted with two due runs and a subscriber on a refusing port, which also checks the failed attempts are recorded for retry. `deployment.deleted` remains unemitted: there is no `DELETE` route for a deployment in any API route module.

- Publishes `deployment.archived`, so the route that ends a deployment's life stops being silent. `POST /v1/deployments/{id}/archive` marked the row archived and returned it while subscribers heard nothing — and this is the event a receiver cannot afford to miss, because missing it means continuing to track a schedule that will never run again. The published row gives it two causes (`订阅Webhook.md:62`): a direct archive, or the deployment's agent having been archived. Only the **direct** cause is implemented here. The second does not exist — `POST /v1/agents/{id}/archive` (`src/api/routes/agents.ts:164`) updates only the `agents` table, and `src/core/operations/scheduler.ts` reads deployments and re-arms `next_run_at` / `last_run_at` without ever archiving one — and the rule it depends on has no representation either: the published text says a deployment with no schedule is never auto-archived, but `cron` is `NOT NULL` and every create arms `next_run_at`, so "no schedule" is not a state a deployment can be in. That is a behaviour of the scheduler and the agent route with its own prerequisite, so it is recorded in `operations.md` §4 as a gap rather than half-built; a test asserts the cascade's **absence** so that implementing it later has to update the expectation deliberately. The event is published only when the archive actually happened, and **after** the write, so a receiver that resolves the reference at delivery time sees `archived_at` set rather than an unarchived deployment — measured inside the receiver, since a read after the route returns would see it either way. A repeat archive publishes nothing and answers `404`: `archiveById` filters `archived_at IS NULL`, so the second call is not an archive, and the published table states the no-op rule for the sibling resource ("对已归档的环境再次归档不会发出任何事件", `:79`). That case asserts **both** halves — the `404` and the silence — because either alone passes for the wrong reason: a route that never publishes satisfies the silence, and a route that publishes on every call satisfies the `404`. To make this possible the shared `archiveById` helper now reports **what it did** alongside the response it already built, rather than the deployment route copying the `archived_at IS NULL` guard. Three resources share that helper, and only a deployment publishes, so teaching it about deployment webhooks would have been the wrong seam; a second copy of the guard is how two routes come to disagree about when an archive happened. The response is still constructed in the helper and returned unchanged, so the webhook and outcome routes are behaviourally identical — asserted, not assumed, because that is exactly the kind of refactor that changes a caller nobody looked at. `deployment.deleted` remains unemitted: there is no `DELETE` route for a deployment in any API route module, so there is nothing to carry it.

- Publishes `deployment.created`, so a subscription learns a deployment exists — the one thing about it a receiver cannot reconstruct. `POST /v1/deployments` inserted the row, returned `201`, and told nobody. `deployment.updated` (the preceding change) reports changes to something that already existed, so a subscriber that started after the create but before the first update had no way to learn the deployment was there at all: the published table lists `deployment.created` (`订阅Webhook.md:58`) and the runtime produced none of the four `deployment.*` lifecycle names. The event is published **after** the insert, so a receiver that resolves the reference when the event arrives finds the deployment rather than a 404 — and the test measures that ordering **inside the receiver**, by asking the database at delivery time, because a read after the create returns would find the row whichever way round the handler did it. A create that is refused — missing `name`, missing `agent_id`, a schedule with the wrong field count, an invalid time zone, a body that is not an object — fails before the row exists and publishes nothing: there is no id to name, and an event pointing at a row that was never inserted would send a receiver to a 404. A deployment **created already `paused`** publishes only this event, not `deployment.paused`. The pause events report a *transition*, and nothing moved here — there was no unpaused state before it — so publishing one would assert a transition that did not happen, which is the same class of mistake as the no-op events the pause work rules out. Nothing is lost: `deployment.created` names the resource and the published contract says a webhook body is a reference the receiver resolves by `GET`, so the receiver learns the status by fetching it, which is the mechanism the published contract supplies for exactly this. `deployment.archived` was subsequently published for its direct cause by the change above, which took the shared-helper decision noted here; its agent-archived cause and `deployment.deleted` remain unemitted.

- Publishes `deployment.updated`, the last name in the deployment write family with no emitter. `PUT /v1/deployments/{id}` rewrote eight caller-visible fields, returned the updated object, and told nobody — and it is the most commonly called route of the three, because changing a schedule is the ordinary reason to reach for it. The published table gives the event its own trigger ("部署属性已更改（例如，其计划已更新）", `订阅Webhook.md:59`), and the nearest published rule for what counts as a change is stated for the sibling resource: "环境已更新，且至少有一个字段发生了变化。**无操作的更新不会发出任何事件**" (`:78`). That second half is the whole difficulty. Every field `PUT` writes is now compared against the row read before the write, and the event fires only if at least one differs: `name`, `agent_id`, `environment_id`, `cron`, `timezone`, `next_run_at`, `payload`, `metadata`. Two things are deliberately not counted. `status` and `paused_reason` belong to the pause transition, which has dedicated events and which the two pause routes also perform — if this event covered them, `POST /{id}/pause` would have to publish `deployment.updated` too, contradicting the published design of a dedicated event for that transition. `updated_at` moves on every write by construction, so counting it would make the no-op rule unreachable and every `PUT` would publish. A `PUT` that changes both a field and the pause state publishes both events, one per change. The stored `payload` and `metadata` are **serializations**, so the comparison has to be structural: `JSON.stringify` preserves insertion order, which means a text comparison reports a change for the same object re-sent with its keys in another order — a change the caller did not make and cannot avoid, since they do not know the order the server wrote. `equalJsonObject`/`equalJsonValue` in `src/api/routes/operation-helpers.ts` compare parsed values with keys sorted at every level, and a nested case is asserted alongside the key-order one. Resolving every written value into a local before the write is what lets the same values decide both what to store and whether anything changed; reading them twice is how a comparison comes to describe a different write than the one that happened. `deployment.created`, `deployment.archived` and `deployment.deleted` remain unemitted, and are recorded as gaps rather than implied to work.

- Publishes the pause event an update causes, so `deployment.paused` and `deployment.unpaused` follow the state change rather than the route. The preceding change wired up `POST /v1/deployments/{id}/pause` and `/unpause`, and its entry claims that "pausing a deployment publishes `deployment.paused`" — which was true of one route and **false of another that produces the same durable state**. The pause state has a third door: `PUT /v1/deployments/{id}` writes `status` and `paused_reason` straight from the request body, so `PUT {"status": "paused"}` paused a deployment and told no subscriber. A receiver watching for pauses still missed them, and the runtime's own documentation was the thing that was wrong. The real defect was the shape of the rule, not a missing call: "did the pause state change, and which event does that mean?" was written twice as two local booleans in the two pause handlers, so adding a third copy to the update route would have made three — and three copies of a rule that must agree is how they stop agreeing, which is the same failure the shared signing-key derivation was extracted to prevent. The decision now lives in `publishPauseTransition(deps, id, previous, next)` in `src/api/routes/operation-events.ts`, and all three doors call it with the state they read before writing and the state they wrote. That makes the rule impossible to omit: a route can only pass the wrong pair of values, not forget the comparison. The two pause routes were rewritten onto the helper, so their behaviour is asserted again in a new file rather than inferred from the neighbours being green, including a mixed sequence that pauses through the update route and resumes through the pause route and then the reverse — the events are derived from the stored state, so a route holding its own idea of the state would publish a duplicate or nothing. Nothing is published when the state does not move, which now holds at all three doors: a `PUT` re-sending the status already stored, a `PUT` that changes an unrelated field, and a `PUT` on a paused deployment that leaves it paused are all silent. `deployment.updated` is **still not emitted** and is recorded as a gap in `operations.md` §4 — a rename publishes nothing at all, and giving it a trigger means comparing every written field against its stored value to satisfy the published no-op rule for update events.

- Scopes the file listing by the published `scope_id` instead of ignoring it. `GET /v1/files?scope_id=<session_id>` is the call the published contract documents for an agent's deliverables — it is the first line of `tests/unit/session-outputs.test.ts`'s own header — and the handler read no query parameters at all, so it answered with **every** file in the workspace. The response was indistinguishable from a session-scoped listing that happened to contain files the caller did not recognise, so a caller asking for one session's outputs had no way to tell they had been handed the global list. Before this change, `scope_id` was pure decoration: the runtime collected session outputs into the store and recorded which session each belonged to, but the read path that was supposed to filter by it never looked. The filter is applied in the query, so a `scope_id` naming no session returns an **empty page** rather than falling back to the global listing — the fallback is precisely the failure this closes, and "which files does this session have" is answered truthfully by an empty page. Omitting `scope_id` returns the same full listing as before, so the Console and the SDK, which call this route without a scope, are unaffected; a file uploaded through `POST /v1/files` records no session and therefore appears in the full listing and in no scoped one, rather than being attributed to a session that did not create it. Because the route now reads a query parameter it is also covered by the refusal for unimplemented parameters, so `?include_archived=true` is answered by name instead of ignored. No migration: `files.session_id` already existed and was already populated by the output collector — this was a read-path gap, not a schema one.

- Refuses a query parameter a route does not implement, instead of ignoring it. A dropped filter is worse than an error, because the answer is plausible: `GET /v1/sessions?include_archived=true` answered `200` with the same list it would have returned without the parameter, and `GET /v1/deployment_runs?deployment_id=nope` answered `200` with an empty page that is indistinguishable from "this deployment has no runs" and from "you misspelled the parameter". Neither response invited the caller to look again. This is the rule `contracts/anthropic-cma/agents.md` §2 already states for request fields — "Unknown keys and unsupported field values are rejected, not silently discarded" — applied to the query string, where it had no equivalent, and the message names the offending parameter and lists the ones that route accepts so the caller can fix the call rather than guess. The allow-list is passed by the handler that reads the parameters rather than kept in a table in the admission module: a central route-to-parameters table is a second description of the same fact and the kind that drifts, leaving a parameter a handler does read refused by a list maintained somewhere else. The refusal is decided before the resource is looked up, so a request that is wrong in both ways reports the parameter rather than a `404` that would imply it was understood. `beta` is accepted on every route and **ignored**, because 36 published examples put it on the URL (`?beta=true`, and `?beta=true&deployment_id=...`) rather than in a header, so refusing it would break a client built against the published documentation; it is deliberately absent from the advertised list, since that list names parameters that do something and accepting `beta` must not be read as honouring it. - Projects the declared top-level fields of every tool event onto the wire. A tool event persisted its payload in `content[0]` only, while `src/types/cma-protocol.ts` declares `name` and `input` as top-level fields on `agent.tool_use`, `agent.mcp_tool_use` and `agent.custom_tool_use`, `tool_use_id` on `agent.tool_result`, and `custom_tool_use_id` on `user.custom_tool_result`. A client written against the declared type therefore read `undefined` for a value the type promised, and the published tool loop could not run at all: it resolves a blocking event id from `stop_reason.event_ids`, then reads `toolEvent.name` and `toolEvent.input` off the event it found. `toApiEvent` now lifts those fields, and `content` is unchanged — the projection adds fields rather than moving them. The top-level `id` deliberately stays the persisted **event** id, because that is the value the same loop answers with; the tool-call id remains reachable as `content[0].id`. A field the block does not carry is omitted rather than sent as `null`, and no field is projected onto an event type whose declared shape has none.
- Answers a path this runtime does not serve with the structured error envelope instead of the framework's plain-text body. An unmatched request returned HTTP 404 with `content-type: text/plain` and the body `404 Not Found`, while every 404 this runtime raises itself returned `application/json` with `error.type: "not_found"`. A client that decodes `error.type` therefore failed while parsing and reported a transport-shaped error for what is really a not-found, and the two shapes differed by which layer noticed the miss rather than by anything the caller did. The server now registers one fallback, so an unrouted path in any namespace answers `{"error":{"type":"not_found","message":"No route matches this request"}}` as JSON. The fixed message does not echo the requested path and stays distinct from a route's own missing-resource message, so "wrong path" and "wrong id" remain tellable apart. Authentication, throttling, and compatibility admission are mounted before routing, so an unmatched `/v1/*` path still answers `401`, `429`, or an admission `400` when those apply. Mounted routes, their 404 bodies, and the Console surface are unchanged.
- Warns at startup when `config.yaml` model settings are not the ones in effect. The file is a first-start import: it seeds the workspace model provider and, from that, the saved Settings document, and every later start reads the saved document. An operator who edited `model.base_url` in `config.yaml`, restarted, and saw `GET /v1/x/runtime` keep answering with the old endpoint got no explanation, and nothing distinguished the two write paths. Startup now names the difference and which source wins, and names the two `model` keys the import reads and never applies — a concrete `model` id, because an Agent declares its own, and the vendor `options` bag, because the model record this file seeds has no column for one. An agreeing file stays quiet, and only whether an API key was declared is reported, never its value.
- Addresses a `vendor/model` model id to the provider whole instead of truncating it. Every slash-containing model name was split into a provider prefix and a model id, so an endpoint that addresses its models by vendor namespace — OpenRouter and the many OpenAI-compatible gateways shaped like it, including a gateway whose ids are all `vendor/model` — could not be addressed at all: `deepseek/deepseek-v4-flash` reached the upstream as `deepseek-v4-flash`, and the request failed with a 404 for a model that does not exist. A leading token is now read as a provider selector only when some configured provider answers to it (by provider type or by registry name); otherwise the whole reference is the model id and travels unchanged. A reference whose namespace a first-party vendor API cannot serve is still refused rather than forwarded — `api.anthropic.com` cannot answer for `openai/gpt-5.5` — while an `openai_compatible` endpoint is treated as the routing authority for its own namespaces, so a router keeps serving `anthropic/...` and `deepseek/...` side by side. `model_used` and the usage and cost records projected from it now name the id the provider was actually asked for, recorded against the client the registry built, rather than the agent's raw reference.

- Reports a model failure as the configuration mistake it is. A missing model, a provider the workspace has not configured, an unusable provider configuration, and a refused credential all raised the same `internal_error` and moved the session to `failed`, which publishes `session.status_terminated` — a client could not tell a fixable typo from a crashed runtime, and the conversation was reported as over. They now carry the distinct codes `model_not_found`, `model_provider_not_configured`, `model_config_invalid`, and `model_auth_failed`, a provider 404 and 401/403 are classified from their structured status rather than from a string match on the message, and `retry_status` is `not_retryable` for each. A turn that fails with one of them leaves the session idle and resumable, so correcting the provider or the agent's model id and sending the next event is enough.

- Corrects the `docs/api.md` Webhooks section, which still described the published header set as first-attempt-only and a retry as carrying the legacy body signature alone. #314 changed that behaviour and updated the contract, the capability matrix, `docs/api-matrix.md` and this changelog, but missed this passage, so the page documented the reverse of what the runtime does.

- Carries the published webhook delivery headers on every attempt. `attemptDelivery` passed a delivery identity to `postWebhook`, and that identity is what adds `webhook-id`, `webhook-timestamp` and `webhook-signature` beside the legacy body signature; `retryDelivery` called the same helper without one, so a retry sent the legacy signature alone and a receiver that verifies the published set had nothing to verify on a retry. A retry now keeps the delivery id — one delivery stays deduplicable across attempts — and signs `<id>.<this attempt's timestamp>.<body>` with the delivery secret, which is what keeps a receiver's freshness window satisfied. The recorded `signature` column still holds the legacy value, so its meaning does not change.

- Anchors the inbound `/v1` rate-limit window to the request that opened it
  instead of to the wall-clock minute. Every bucket used to be cleared at each
  minute boundary, so two writes 10 ms apart that fell on opposite sides of
  `12:01:00` were both allowed and a one-write budget was spent twice inside 60
  seconds. A window now runs a full minute from its first counted request, so a
  burst straddling a boundary is throttled, and `Retry-After` reports the time
  until the caller's own window expires rather than the time to the next minute.
  Buckets, budgets, exemptions, and the 429 body are unchanged.

- Keeps OpenAI-compatible streaming sessions alive when a gateway fragments a
  tool call across many SSE deltas and emits an empty or missing
  `tool_calls[].type`. The runtime rewrites only that field on the wire, so
  argument fragments and every other byte are preserved and the stream no
  longer aborts with a schema validation failure. Non-SSE and error responses
  are passed through untouched.

- Makes approval-gated tool calls durable and atomic per model step. Every
  confirmation decision, group identifier, and paired tool result is stored in
  the append-only event log; a model continuation begins only after the full
  group is resolved. Sessions expose `requires_action` directly while pending.
- Makes Console session replay sequence-aware. The Console now treats the
  resumable event tail as the single durable source, merges REST snapshots by
  sequence, and never advances a replay cursor for transient text chunks.
- Adds `seq` and immutable `metadata` to public event responses and aligns SSE
  envelopes with REST. Model-attributed event projections include the selected
  model and provider stop reason when available.
- Records the session budget capability as `planned` instead of `partial`. The
  matrix entry claimed enforcement, pause semantics, the settlement-event
  whitelist, a session-wide ceiling and an operator-supplied cost profile, while
  `session-budget.ts`, `cost-profile.ts`, and their tests are absent from the
  tree: nothing priced model consumption and no session accepted a budget. The
  contract documents disagreed with each other as well, `sessions.md` calling the
  budget `not_applicable` and `unsupported.md` calling it `partial`. The entry and
  both documents now state that the design is published and nothing implements it.

- Holds the SQLite state database to the connection settings the runtime was
  already assuming. `src/core/db/database.ts` opened the workspace database with
  `journal_mode = WAL` and `foreign_keys = ON` and nothing else: no
  `busy_timeout`, no `synchronous`, no `trusted_schema`, and no read-back, so a
  pragma that did not take effect — on another platform, another Node version or
  another driver — left the runtime running with a weaker guarantee than it
  reported. A connection now sets and then verifies
  `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`,
  `synchronous=FULL` and `trusted_schema=OFF`, and a value that does not read
  back refuses startup instead of being logged and ignored. The two macOS-only
  pragmas in the recipe this follows (`fullfsync` and `checkpoint_fullfsync`) are
  deliberately not claimed: Node's bundled SQLite defines no
  `SQLITE_ENABLE_FULLFSYNC`, and the pragma is a flag that reads back as set on
  any platform, so verifying it could not show the guarantee was in effect, while
  `synchronous=FULL` is the durability guarantee that applies here. An
  in-memory database is accepted with the one journal SQLite can give it, and
  every other setting is verified for it too. `Database.transaction()` now opens
  with `BEGIN IMMEDIATE`, so the write lock is taken when the transaction starts
  rather than at its first write: with the CLI and a server pointed at the same
  file, a deferred transaction could hold a read snapshot that another process's
  commit made unpromotable, which failed with `SQLITE_BUSY_SNAPSHOT` after the
  transaction body had already run. The same conflict is now a bounded wait.
  Existing workspaces need no migration — the settings are connection-level and
  the WAL conversion happens on open.

### Security

- Redacts credential secrets from values that are logged or returned. A redactor
  bound to one injection bundle replaces every secret it holds wherever it appears,
  including nested objects and arrays, and `clear()` drops the held secrets so the
  redactor cannot be reused after the turn ends. A secret belonging to a different
  bundle is not redacted, and a value containing no secret is returned unchanged.
  The canonical credential shape rejects an unknown field rather than ignoring it.

- Stops persisting raw model reasoning in the public event log. `agent.thinking`
  is now emitted as a content-free progress signal carrying
  `metadata.signal = "reasoning"`, so reasoning traces that echo tool output are
  no longer readable through the REST event listing or the SSE stream.
- Adds credential-scoped, in-process inbound rate limiting after authentication.
  Protected runtimes use independent read/write fixed windows, structured 429
  responses, health/preflight exemptions, dynamic managed-key posture, and
  environment overrides; open local runtimes remain unlimited by default.

- Enforces credential vault network policy at the injection boundary. Limited
  credentials require a verified matching target host before decryption; denied
  credentials are omitted from injection outputs, audited without secret values,
  and do not update `last_used_at`. This helper boundary does not yet claim
  universal web/MCP/custom-tool caller propagation.

- Admits CMA `/v1` requests that use `x-api-key` or Anthropic compatibility
  headers before route business logic: required version/beta headers are
  validated with stable structured errors, memory-store routes require their
  own memory beta, and existing `Authorization: Bearer` requests without CMA
  headers retain their behavior. Authentication accepts exactly one credential
  source per request; dual `Authorization` and `x-api-key` inputs are rejected.
  Memory-store requests reject combined managed-agents and agent-memory betas,
  while the documented memory listing accepts either beta.
- Updates `prefix-safe-json` `0.4.2` -> `0.4.3`, a security release fixing
  GHSA-3xpw-9694-2xxp: the AI SDK adapter used to silently drop raw stream
  events once it had already observed a call's own terminal, and
  `takeDecision()` used to read a decision snapshot frozen at `finish()`
  time instead of live coordinator diagnostics, so late or contradictory
  lifecycle evidence for a tool call could fail to revoke its execution
  authority. No public API change. Confirmed the exact vulnerable-then-fixed
  behavior against this integration's own `createAiSdkV4ExecutionGuard`
  wrapper (`tests/integration/post-terminal-authority.test.ts`), not just
  the library's own test suite.

- Stops an Environment's hosting declaration from silently becoming local
  execution. `hosting_type` was written but never read by the resolver, so an
  Environment that asked for `cloud`, `docker`, or `kubernetes` and did not also
  name a `sandbox_provider` ran on the local backend — the one backend that is
  not a security boundary — and an unusable declaration was indistinguishable
  from no declaration at all. An Environment is now resolved fail-closed:
  `cloud` names hosting on machines this runtime does not own, has no backend
  here, and is refused rather than lowered to local; an unknown hosting type is
  refused with `unsupported_hosting_type`; a config that is not valid JSON, not a
  JSON object, or that declares a hosting field which is not a name is refused
  with `invalid_environment_config`; and a declared
  `docker`, `kubernetes`, or `self_hosted` hosting type now selects that backend.
  An explicit `sandbox_provider` continues to win over `hosting_type` and is
  preserved verbatim, so an out-of-tree provider still reaches the registry,
  which rejects an unregistered name by name. The refusal is raised when the
  session is created or when an event is admitted — before any row is written
  and before the session can accept work — and is served as a `400` carrying the
  stable error code, instead of surfacing later as a provisioning failure. The
  workspace default seed refuses the same inputs rather than reducing them to
  local. Read paths are unaffected: `GET /v1/environments` reports the backend an
  Environment declares, so a Kubernetes Environment is no longer projected as
  `cloud`, and a declared hosting type is echoed even when this build refuses to
  execute it, so an operator can still see what the record says.
