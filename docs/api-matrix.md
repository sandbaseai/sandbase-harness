# Versioned API Matrix

This matrix tracks the public `/v1` API shape for the open-source runtime. It
is a compatibility guide for SDK authors and integrators; it is not a promise
that every Claude hosted capability exists locally.

## Version Policy

- The current public namespace is `/v1`.
- Resource ids are opaque.
- Canonical `/v1` collections use `{ data, prev_page, next_page }` and the `/v1/x`
  extension collections use `{ data, has_more, first_id, last_id }`. The conversion
  runs collection by collection, so a collection not yet listed in
  `contracts/anthropic-cma/pagination.md` §4 still answers with the local envelope
  under either prefix; the contract names which is which.
- Errors use `{ error: { type, message } }`. A rejected compatibility
  request also carries a stable `error.code` from the published
  admission-code set. A path the server does not serve answers the same
  envelope as JSON with `not_found`, rather than the framework's plain-text
  body, so one decoder handles an unrouted path and a missing resource alike.
- CMA requests using `x-api-key`, `anthropic-version`, or `anthropic-beta` are
  admitted before `/v1` CMA handlers: version `2023-06-01` and beta
  `managed-agents-2026-04-01` are required, except `/v1/memory_stores` routes
  require `agent-memory-2026-07-22`. Memory-store requests reject a combined
  managed-agents and agent-memory beta; `GET /v1/memory_stores/{id}/memories`
  accepts either beta. A request must carry exactly one of `Authorization` or
  `x-api-key`; existing bearer requests without CMA compatibility headers remain
  supported.

- A protected runtime applies best-effort in-process fixed-window inbound throttling after authentication: 300 write requests/minute and 1200 read requests/minute by default, credential-scoped buckets, structured `429` responses, and no counting for `/v1/x/health` or CORS `OPTIONS` preflight. Open local runtimes are unlimited by default; environment overrides are documented in `docs/api.md`.

## `/v1` Resource Matrix

| Area | Endpoint group | Status | Notes |
| --- | --- | --- | --- |
| Session archive | `/v1/sessions/{id}/archive` | Supported | Archives an idle session, emits `session.status_terminated`, releases its sandbox, and returns the session with `archived_at`. Running sessions return `session_running` until interrupted; repeated archive calls are idempotent; new events and messages return `session_archived`. Archived sessions leave the collection unless `include_archived=true` is sent. |
| Agents | `/v1/agents` | Supported | Create, list, retrieve, update, archive, and list versions. On create, omitted or null `system` normalizes to an empty string; updates keep an omitted prompt and clear it with null or an empty string. Create and update validate `web_fetch` and `web_search` domain lists against the published grammar and reject a malformed list with `invalid_request_error` naming the list and index. The `model` field accepts the canonical object form: `effort` and `speed` are stored in the model profile and returned by every read — the agent read, the version read, and a session's frozen snapshot — and on the Anthropic provider both execute under a model capability table (`output_config.effort`; `speed: "fast"` plus the fast-mode beta; adaptive-thinking models get `thinking: {type: "adaptive", display: "omitted"}`), with admission refusing a level or speed a listed model cannot take, while an unrecognized or unsupported field is refused by name with `unsupported_model_field`. | Create and update also cross-check `mcp_servers` against the `mcp_toolset` entries that bind it, refusing a toolset naming an undeclared server, a declared server no toolset binds, and a duplicate server name. `PUT` and `PATCH` both accept a partial definition and apply the same update semantics: an omitted field keeps its value, list fields replace wholesale, `metadata` merges per key with an explicit `null` deleting that key, `null` clears a clearable field, `name` and `model` cannot be cleared, and an unknown field is rejected. A canonical `multiagent` roster is refused on both paths with a message naming the capability `multiagent-roster`, because no thread, coordinator, or advisor surface exists in this runtime; `enable_general_subagent` is accepted on both paths as the local single-level delegation extension. The merged definition is revalidated against the full schema before it is persisted. Create and update also accept a custom tool either as a canonical `custom` entry or in the legacy `custom_toolset` grouping, and project one canonical shape on read. | Every memory write records an immutable version row carrying the per-memory monotonic version number, the content hash and byte size as written, the change kind, and the session that made it, so a memory's history is reconstructable after the live row has been overwritten. | An MCP tool is governed by the permission policy of the toolset that binds its server: the toolset kind supplies the default (`always_ask` for MCP, `always_allow` for the built-in toolset) and an explicit per-tool or toolset-wide policy overrides it. A tool the server exposed but the agent never named is admitted under the same default and carries no local `execute` until approved; a `never_allow` tool is not admitted at all. An opt-in `auto` policy evaluates each call with a local model verdict — `allow` runs it, `deny` returns a flagged error result without running, `ask` parks it for `user.tool_confirmation`, and any evaluator failure degrades to `ask`/`indeterminate` rather than allowing; the Pi engine refuses `auto` with `pi_tool_policy_not_supported`. |
| Sessions | `/v1/sessions` | Supported | Create, list, retrieve, update, stop, permanently delete, durable event ingestion/listing, sequence-resumable SSE, and message convenience endpoint A stream connection with a `Last-Event-ID` cursor replays the stored events after it and then goes live; without one it carries live events only, and a cursor that is not the numeric `seq` is refused with a `400` before the stream opens. Keepalives are `event: ping` with a JSON body and no id. A stream connection can opt into token-level previews with a repeated `event_deltas[]` parameter for `agent.message` and `agent.thinking`; preview frames carry no id and are never persisted. A live stream writes `session.deleted` and closes when its session is permanently deleted. | Creation also accepts an optional `initial_events` array of `user.message` and `user.define_outcome` events that are validated and written in the same transaction, so a non-empty list yields a `running` session whose log already holds them and a rejected batch leaves no session behind. A `user.define_outcome` event carries the session's success criteria — a `description`, a `rubric` (inline text or a file reference) and a `max_iterations` budget that defaults to 3 and is capped at 20 — and its payload is projected back onto the event listing; the same normalization and its `invalid_define_outcome` refusal apply to a live `POST /v1/sessions/{id}/events`. Create accepts optional `loop_engine`; the resolved engine is persisted and frozen on the session. Unavailable engines return `loop_engine_not_supported`, unknown values return `loop_engine_invalid`, and rejected requests leave no session row or event. The deprecated local `/stop` alias interrupts the active turn, drains execution, and returns a full session envelope. Successful builtin and Pi interruptions retain the sandbox for another message; idle stops are no-ops and already terminal sessions return `409`. Unconfirmed Pi cleanup still fails closed. The alias is removed next version; delete refuses running sessions with `session_running`, otherwise removes the session row, event history, session-owned state, snapshots, and generated files and returns `{id, type: "session_deleted"}`. Public session status is only `idle`, `running`, `rescheduling`, or `terminated`: approval waits are `idle` with a `requires_action` stop reason, a transient model failure being retried is `rescheduling` (a `session.error` with `retry_status: {"type": "retrying"}` then `session.status_rescheduled`, `session.status_running` again on recovery, and `exhausted` plus a `retries_exhausted` idle once the policy gives up — the session stays usable), all terminal internal states are `terminated`, and failed sessions refuse new events and messages with `409` before persistence or execution. The list takes the published parameter set — a repeatable `statuses`/`statuses[]` filter that covers every internal state in each requested public group (`rescheduling` selects sessions retrying a transient model failure), `order` by `created_at`, `include_archived`, `agent_id` with `agent_version` beside it, `memory_store_id`, `deployment_id`, and `created_at[gt|gte|lt|lte]` bounds — and a `page` cursor binds the ordering and creation window it was issued under while other filters may change across a replay. Event envelopes include `seq`, immutable metadata, and optional model/token/stop-reason/duration metadata. Every model request brackets itself with a `span.model_request_start`/`span.model_request_end` pair — one `prepareStep` to `onStepFinish` cycle is one request, so middleware retries still produce exactly one pair — and the end carries the published `model_request_start_id`, `is_error` (`null` on rows persisted before the flag), and `model_usage` beside the local extension fields — `model_usage.speed` appears when the request ran in fast mode. A session whose model resolves to an `anthropic` provider sends the platform's automatic prompt caching as explicit `cache_control: {type: "ephemeral"}` markers on the system prompt, the last tool definition, and the second-to-last message — three breakpoints inside the four-slot cap at the default TTL — while every other provider type's request is sent unmarked. A `session.usage` snapshot event is written immediately before every `session.status_idle`, carrying `input_tokens` (the uncached share only), `output_tokens`, the prompt-cache counters `cache_read_input_tokens` and `cache_creation` split by TTL, and `active_seconds`; it also carries `list_cost` when every model the session used has a configured list price, the session's `budget` or `null`, and zeroed `server_tool_use` counters, because this runtime has no built-in web tool. Creation also accepts an optional `budget` (`{type: "limit", max_list_cost: {amount, currency: "USD"}}`) priced from an operator-supplied cost profile; a session whose model has no list price is refused a budget with `model_not_budgetable` rather than metered against an invented rate, and once the ceiling is reached a work-starting event is refused with `budget_reached` while events that settle in-flight work are still accepted. A turn that crosses the cap mid-run stops after that step and idles with `stop_reason: {"type": "budget_reached"}` — a tool call stranded by the stop is settled so the log stays paired — and an accepted budget update or removal resumes the session on its own without a `user.message`. A declared outcome stops at the ceiling too, closing with `result: "budget_reached"` rather than starting another grading pass or turn. `agent.mcp_tool_use` and `agent.mcp_tool_result` events carry `mcp_server_name` (and results carry `mcp_tool_use_id`) so two servers exposing the same tool name stay distinguishable. Governed `agent.tool_use` and `agent.mcp_tool_use` events project `evaluated_permission` (`allow`/`ask`/`deny`) and `evaluation` (the policy arm that produced it — `always_allow`, `always_ask`, or `auto` carrying the per-call verdict and `reason_code`). Pi stdout final replies and native tool trajectories use the same event history; transient deltas are not replayed; Pi native tools remain outside Harness approval and sandbox path policy, and a native tool declared `always_ask` is gated by the session's own managed Pi extension before it executes, with one durable pending record per call that only a single decision can consume, and that decision is a person's unless the operator selected `loop_engine.options.approval_mode: "preauthorized_once"`, whose platform-owned rule answers one call at a time and is recorded as `confirmation_source: "platform"` rather than as a human approval. `user.steer` is accepted on a live Pi session as its own event, never as a `user.message`: it is written to the running turn's input channel instead of being queued behind it, and the response carries a receipt whose `state` is `delivered`, `duplicate` (the same `input_id` with the same text), `conflict` (the same `input_id` with different text), `rejected` (no turn was accepting steering, so resending is safe), or `outcome_unknown` (the write was not acknowledged and must never be replayed); `accepted` is false for `rejected` and `conflict` only, one steer may be in flight per turn, admission closes before `turn_complete` and accepted receipts settle before it, and a steer for a session with no turn in flight or a child that is gone is refused rather than buffered. Pi cleanup keeps distinct internal `cancelled`, `timed_out`, or `cleanup_pending` outcomes rather than fabricated success; each projects to public `terminated`, with details in the event log. | Creation validates web-tool domain lists on the supplied agent definition and rejects a malformed list before the session is persisted. | `POST /v1/sessions/{id}` updates a session in place: `agent` admits only `tools` and `mcp_servers`, which replace wholesale and are merged onto the definition the session resolves — its own snapshot or the agent it follows — then validated like an agent definition and materialized as `agent_definition` without touching the agent row; `metadata` is a merge patch (`null` per key removes it, `null` for the field is no change); `title` replaces with `null` clearing, and `budget` moves the ceiling under the budget rules (`budget_create_only`, `budget_not_raised`, `model_not_budgetable`, `budget_invalid_*`) in any non-terminal state. `vault_ids` is refused with `vault_ids_not_updatable`, another `agent` field with `agent_field_not_updatable`, and a terminated or archived session with `session_terminated`; an agent change also needs an idle session (`session_not_idle` while running), while `title`, `metadata`, and `budget` move in any non-terminal state. All admitted changes land in one transaction with exactly one `session.updated` event carrying only the changed fields — the full agent snapshot, the new ceiling or `null`, the whole post-update metadata bag (absent when cleared), the new title — and a no-op emits nothing; the new configuration applies from the next turn, with MCP connections torn down so they reconnect under the updated definition. | Creation also accepts the `agent_with_overrides` reference form, which runs a pinned or current agent version with any of `model`, `system`, `tools`, `mcp_servers`, or `skills` replaced for that session only under the tri-state rule: an omitted field is inherited, `null` (or `[]` for a list) clears it, and a value replaces it wholesale. The resolved definition is frozen as the session's own snapshot and is what capability admission judges, while the agent row and its version list are untouched. A refusal is a 400 raised before the session row exists, carrying `agent_model_required`, `agent_tools_cleared_with_skills`, `agent_mcp_server_not_found`, `invalid_agent_override_field`, `invalid_agent_overrides`, or `invalid_agent_ref`. Every session object carries the published fields: `budget` is always present (`null` when the session has no ceiling, whether never set or removed), `stats` reports `active_seconds` summed from the `running` intervals in the event log and `duration_seconds` counted from creation (frozen at the last update once terminal or archived), and the materialized `agent` pins `version` to the session snapshot with `multiagent: null`. `loop_engine` is the only key beyond the published set; `outcome_evaluations` is projected from the declaration and evaluation spans on create, retrieve, and list — one entry per `user.define_outcome`, `pending`/`running`/`evaluating` in progress and the terminal end-span verdict once closed — and a `user.define_outcome` event carries the admission-assigned `outcome_id` its spans and its session entry join on. |
| Runs | `/v1/runs` | Supported | Start one turn and return its result. `response_mode` selects `wait` (200 with output and usage), `sse` (event stream), or `async` (202 with a query handle); `max_wait_seconds` bounds only the wait and answers 202 with `wait_deadline_reached` when it elapses. Pre-execution refusals answer with their own status, and a mid-run failure is recorded once as `session.error`. Session budgets are not part of this endpoint. `agent` accepts only the id string and the pinned object form; the `agent_with_overrides` form is refused with a message naming the reason rather than accepted and ignored. |
| Session errors | `session.error` event | Supported | Every failed turn appends one `session.error` whose top-level `error` object carries an official `type`, a `message`, an object `retry_status`, and the runtime's own `code`. The disposition is derived from the code, an aborted turn records nothing, and events persisted with the legacy string disposition are normalized on read. |
| System messages | `system.message` event | Supported | Accepted as an inbound session event alongside `user.*`, validated against the content-block vocabulary and the 1000-block ceiling, and projected as a `system` role turn that persists for every later turn. |
| SDK compatibility headers | `managed-agents/sdk` | Supported | The first-party SDK sends `anthropic-version` plus the family beta on every canonical `/v1/...` request, chooses the memory beta for memory-store paths, sends nothing on `/v1/x/...`, and lets a caller override the derived beta. |
| Session artifacts | `/v1/sessions/{id}/artifacts` | Supported | Create/list artifact records and fetch content. |
| Handoff bundles | `/v1/x/handoff-bundles` | Supported | Export one session as recorded evidence. `POST /v1/x/sessions/{id}/handoff-bundle` builds and stores a bundle, `GET /v1/x/handoff-bundles` lists stored bundles newest first, and `GET /v1/x/handoff-bundles/{id}` returns a stored payload unchanged. RO-Crate 1.1, BagIt sha512 manifests, and an in-toto statement in a DSSE envelope signed by a runtime-derived Ed25519 key carry the packaging. Replay is `recorded_replay` only, with tools never re-executed and model requests never re-issued; `resume` and `fresh_run` are declared unsupported. Message bodies and file bytes are excluded unless opted in, and credential secrets are never included. |
| Files | `/v1/files` | Supported | Upload/list/retrieve/delete workspace files and fetch content. A file attached to a session takes a logical `mount_path` that the runtime maps under its own mount root, so the sandbox layout is never part of the public field. That mount is written at provisioning and announced to the agent: a session with a file or repository resource carries a `# Session Resources` section in its system prompt naming each mount path, and on the `local` backend also the sandbox-relative spelling a shell command needs. The `local` backend maps the canonical `/mnt/session/uploads` root into the session's sandbox and the bytes are readable there, and `docker` serves the root verbatim — a container's filesystem is the sandbox, so the canonical path is the real path. The runtime does not serve that root on `kubernetes` (whose acceptance of the root was never exercised against a cluster) ; a `self_hosted` worker downloads each attached file through its session work token and writes it at the mount path under its own root (`<workdir>/mnt/session/uploads/...`). A session that declares a resource its backend cannot serve is refused when it is created, with `resource_not_mountable`, before any session row, resource instance, or event is written. | Files an agent writes under `/mnt/session/outputs/` are published as session-scoped records after the turn, idempotently per (session, sandbox path). |
| Environments | `/v1/environments` | Supported | Create/list/retrieve/update/delete/archive environment templates. `POST /v1/environments/{id}` is the published update verb (`PUT` remains an alias) with patch semantics — `metadata` merges key-by-key and deletes a key on `null` or `""`, `description: null` clears, omitted fields are preserved. `DELETE /v1/environments/{id}` removes the row physically and answers `{id, type: "environment_deleted"}`; it is refused with `environment_protected` for `env_default` and with `environment_in_use` while any session — running or finished — still references the environment, because session history keeps the environment it ran on. The published `config` shape is read rather than stored and ignored: `config.type` and the local `config.hosting_type` are two spellings of one hosting axis, either resolves through the same backend vocabulary, a non-string declaration is refused instead of read as undeclared, and two spellings that disagree are refused with `invalid_environment_config` rather than resolved by precedence. `cloud` — in either spelling — is the published "the platform decides" value: it is accepted, stored as declared, and sessions on it provision on the workspace's configured default backend, which `effective_sandbox_provider` reports distinctly from the declaration. An unknown hosting type is refused with `unsupported_hosting_type` naming the types this build can execute, so an environment it cannot run is never accepted and then failed at session start. `config.networking` is normalized into the recorded local `config.network` under the local key names (`allow_mcp_servers` → `allow_mcp_server_network_access`, `allow_package_managers` → `allow_package_manager_network_access`), with `limited` and a denied permission as the fail-closed defaults, the published key consumed rather than stored beside its local twin, and two disagreeing spellings refused. A request that names one spelling replaces the stored declaration in the other, so a row written with the published spelling can be repaired or renamed through the local one, and a stored declaration that cannot be resolved reports a null `effective_sandbox_provider` rather than a backend. The response projects the published `config` shape — `config.type`, `config.networking`, `config.packages` — beside `effective_sandbox_provider`, with `packages_enforced` and `networking_enforced` marked `false`: the policy and package declarations are recorded, not applied, so a declared limit does not change what a session can reach and no package is installed. |
| Environment worker keys | `/v1/environments/{id}/worker-keys` | Advanced | Create/list/revoke scoped self-hosted worker keys. Only the SHA-256 hash is stored, so `secret_key` is returned exactly once and list and revoke carry `key_prefix`; a claim presenting the key is scoped to the issuing environment and a revoked, expired, or unknown key is refused before any work item changes hands. Not needed for the default local runtime. |
| Environment work queue | `/v1/environments/{id}/work-items` | Advanced | Inspect recent queued self-hosted work and queue stats; not needed for the default local runtime. |
| Environment work | `/v1/environments/{id}/work` | Advanced | The full published Work API over the local tool-execution queue: `poll` claims the oldest claimable item with a per-claim `secret` (`mawt_` session token plus `api_base_url`), `ack` commits the claim, `heartbeat` renews the heartbeat lease with `NO_HEARTBEAT` first-claim and `expected_last_heartbeat` optimistic concurrency, `POST /{workId}` merges metadata, `stop` writes the stop marker, and the management reads — list with a keyset `page` cursor, retrieve, and `stats` (`depth`, `pending`, `oldest_queued_at`, `workers_polling`) — project the same queue. The `mawt_` token also authorizes the worker's session-level calls: its own session's retrieve and event surface (answers limited to tool-result types) and the attached memory stores' `memories` routes, with `read_only` attachments refusing writes. The queue also carries a `custom_tool` kind: a session's persisted `agent.custom_tool_use` is enqueued for the environment's workers, and the completion is injected back as the parked call's `user.custom_tool_result`. `data` is always `{type: "session", id}`, per-item `desired_ttl_seconds` is reported not applied, and results stay on `/v1/x/worker/complete`. See `contracts/anthropic-cma/work.md`. |
| Credential vaults | `/v1/vaults` and `/v1/credential-vaults` | Supported | Create/list/retrieve/update/archive/delete vaults. `POST /{id}` applies a `display_name`/`description`/`metadata` patch (`vault_archived` refuses an archived vault); `DELETE /{id}` physically removes the vault and its credentials, returns the `vault_deleted` tombstone, and answers `vault_in_use` only while a non-terminal session references it. The same router is mounted at both prefixes; the underscore spelling this row and its neighbours used to carry is not a route the runtime serves. |
| Vault credentials | `/v1/vaults/{id}/credentials` and `/v1/credential-vaults/{id}/credentials` | Supported | Create/list/retrieve/update/archive/delete credentials with secret redaction, replace a stored secret by rotation, and mark one used. `POST /{credential_id}` is the published update: `display_name`/`metadata` patch plus a type-discriminated `auth` partial update where `auth.type` is immutable, structural fields are locked, a secret value re-encrypts and writes a `rotate` audit event, and `expires_at`/`refresh` answer with warnings rather than persisting. A create write accepts the canonical nested `auth` object or the flat legacy spelling, and a read carries the canonical `display_name` / `auth` projection beside the local fields — never the secret material. `DELETE` is physical and returns the `vault_credential_deleted` tombstone while the audit trail survives at vault scope. |
| Credential audit | `/v1/credential-vaults/{id}/audit` and `/v1/credential-vaults/{id}/credentials/{credential_id}/audit` | Supported | Lists rotation, use, injection and denial events at vault or credential scope, newest first, without secret material; the trail survives deletion. |
| Memory stores | `/v1/memory_stores` | Supported | Create/list/retrieve/update/archive/delete stores. |
| Dreams | `/v1/dreams` | Supported | Memory-consolidation jobs (`drm_` ids) with create/list/retrieve/cancel/archive and a `pending → running → completed/failed/canceled` lifecycle. `inputs` names exactly one memory store — mounted read-only into the pipeline, never modified by default — plus 1–100 session ids whose transcripts are packed into the dream context. The pipeline runs as an internal session exposed on `dream.session_id` (its event stream stays auditable after archival), executes on the existing operations tick rather than a dedicated worker, and writes into a new store seeded as a copy of the input under `create_new` (the default) or into the input store under `update_existing`. `POST` accepts `model` (string or `{id, speed}`) with precedence over the `dreams.model` runtime setting, which itself overrides the workspace default. A failed or canceled dream keeps its partial output store; cancel stops and archives the pipeline session; archive is terminal-only. Archived dreams leave default listings unless `include_archived=true`. The `dreaming-2026-04-21` family beta is admitted on the resource without being required, so the official SDK's dreams client reaches the route. See `contracts/anthropic-cma/dreams.md`. |
| Memory records | `/v1/memory_stores/{id}/memories` | Supported | Create/list/retrieve/update/delete memory records under the published object shape (`memory_store_id`, `content_sha256`, `memory_version_id`). Content is capped at 100 kB measured in bytes, a store holds at most 10,000 memories, `path_prefix` and `depth` scope a list, `view` selects the `basic`/`full` projection with the published per-endpoint default, a `content_sha256` precondition refuses a stale write with `memory_precondition_failed_error` and reports the current hash, a path collision is a `memory_path_conflict_error`, delete answers `{id, type: "memory_deleted"}` and accepts `expected_content_sha256`, and `POST` is the published update verb with `PUT` as a deprecated alias. Versions list by `memory_id`/`operation`/`view` and a non-head version can be redacted (`memory_version_is_head` refuses the head). |
| Session memory mounts | Session creation `resources[]` | Supported | Mount up to eight memory stores at whole-segment paths; file tools persist mounted reads/writes through `memory_records`, read-only mounts reject writes, and existing-file updates require a content precondition. |
| Skills | `/v1/skills` | Supported | List built-in/custom skills and upload validated custom ZIPs. Versions are first-class under `/v1/skills/{id}/versions`: upload a new package with the same format as skill creation (the frontmatter `name` must match the skill's, `409` otherwise), list newest first, retrieve metadata, download the stored package as a zip archive (the literal `latest` addresses the current version), and delete a version (`skill_version_deleted`) with the only remaining version refused at `409`. The skill's `latest_version`/`latest_version_id` repoints at the newest survivor on deletion, and an agent skill reference can pin `version`; a pin naming a deleted version mounts nothing. Built-in `anthropic` skills answer version metadata read-only. Assigned packages are also materialized into the session sandbox under `skills/<name>/` (inside `/workspace` on docker) when it is provisioned — scripts and references are real files the file/shell tools can reach — and a `worker run` materializes them under `<workdir>/skills/<name>/` through the session work token, which may download only the versions its session's agent assigns. |
| API keys | `/v1/api-keys` | Supported | List/create/delete managed keys; config/env keys are read-only. |
| Webhooks | `/v1/webhooks` | Advanced | Create/list/update/archive, test deliveries, delivery attempts, retry due deliveries, and a signing-secret rotation window. Every attempt carries the Standard Webhooks v1 headers, signed with the subscription's own `whsec_` secret that creation returns once, with the signature covering id, timestamp, and body, the published `{type: "event", id, created_at, data: {type, id, organization_id, workspace_id}}` envelope on every attempt, `webhook-id` carrying the event id unchanged across retries, `rotate-secret` keeping the previous secret valid in a second signature until `retire-secret` closes the window or it expires after the deployment's rotation window (24 hours by default, `MANAGED_AGENTS_WEBHOOK_ROTATION_WINDOW_SECONDS`), and constant-time verification. The runtime projects each durable event as it is broadcast and ticks every 60 seconds for due retries, so an unwatched runtime delivers; `dispatch` and `retry-due` remain for on-demand passes. A failed attempt is retried up to three times with jittered 5–120 s backoff; an endpoint that answers a redirect, or fails without interruption for a sustained-failure window that defaults to 10 minutes and that a deployment sets with `MANAGED_AGENTS_WEBHOOK_SUSTAINED_FAILURE_WINDOW_SECONDS`, is disabled with a `disabled_reason`, and private-address screening is available behind `MANAGED_AGENTS_WEBHOOK_SCREEN_PRIVATE_ADDRESSES`. Subscriptions name events from the official catalog — `*`, `prefix.*`, and unknown names are refused with `400`, as are the four published names with no producing surface (`session.thread_*`, `agent.deleted`) — the session stream reaches subscribers only through the published-name projection, every admitted name fires from a real transition including the coarse session lifecycle events (`pending` at creation, `running`/`idled`/`requires_action` on the status stream), and resource lifecycle events across sessions, agents, environments, vaults, memory stores, and deployments are published on transitions. |
| Scheduled deployments | `/v1/deployments` and `/v1/scheduled-deployments` | Advanced | Create/list/update/archive/run/run-due/delete schedules with the published object shape (`type: "deployment"`, `depl_` ids, `{type, id, version}` agent pin, `environment_id`, `initial_events` — including `system.message` — `resources`, `vault_ids`, `budget`, `metadata`, a `schedule` object with `upcoming_runs_at` or `null` for a manual-only deployment). A cron expression is evaluated in the deployment's own timezone, with spring-forward gaps reported as having no run and fall-back overlaps resolved deterministically. Failure is asymmetric per the published contract: an archived or missing bound agent archives the deployment with no run; a recoverable `session_rate_limited_error` records a failed run only; other classified failures (`environment_archived_error`, `vault_not_found_error`, …) record the run and auto-pause the deployment with `paused_reason.error` mirroring the run error. | Worker queue | `/v1/x/worker/claim`, `/v1/x/worker/accept`, `/v1/x/worker/heartbeat`, `/v1/x/worker/complete` | Advanced | Used by `managed-agents worker poll` when running a self-hosted worker. A claim carries a lease; `heartbeat` renews it so an item outliving the lease is not reclaimed while its worker is still running it, and `accept` confirms the claim immediately before an item is run, so an item whose lease window passed between claiming and starting is not executed as well as reclaimed. The server's own bounded wait on an item reports why it gave up rather than only that time passed: `work_queue_timeout` when no worker ever claimed it, `work_outcome_unknown` when a worker claimed it and never answered, and `work_lease_lost` when the session ended and stopped it. A held item whose executor never accepted it is also `work_outcome_unknown`, and the give-up is recorded on the row, but the item stays reclaimable so the queue re-offers and runs it rather than losing it. Acceptance is the line: an item whose lease lapses without an accepted ack is handed to the next worker because nothing ran, while one whose lease lapses after the holder accepted it is never handed out again - the effect may already have happened - and moves to status `unknown`, which is not claimable and refuses a late completion. An item's status is one of `queued`, `accepted`, `applied`, `failed` or `unknown`, and the chain is about commitment rather than about who holds the row: `queued` covers both an untouched item and one held under a lease but not yet accepted, `accepted` is the point from which the effect may already have happened, and only `queued` is claimable. Workspaces from before this vocabulary are renamed once on migration, with the old `pending`/`claimed`/`done` surviving only as that mapping. |

## Unsupported Official Routes

Known operations in these official SDK resource families return HTTP 400
`unsupported_capability`, with a capability id and reason in
`error.details.capabilities`. Refusals run after authentication, rate limiting,
and compatibility-header admission, and perform no persistence or execution.
The mounted method/path inventory is listed in
[`contracts/anthropic-cma/routes.md`](../contracts/anthropic-cma/routes.md);
unknown methods or paths are not broadly intercepted.

Tunnels and user profiles recognize the SDK's native
`mcp-tunnels-2026-06-22` and `user-profiles-2026-08-18` betas respectively, as
well as the canonical managed-agents beta. These native betas are scoped to
their refusal resource families and do not admit a supported resource or
bypass version validation. The dreams family beta is handled the same way but
its family is now implemented, not refused.

| Official resource | Capability id | Reason |
| --- | --- | --- |
| `/v1/tunnels` and certificate/token actions | `mcp-tunnel` | Hosted connectivity is outside the local-first scope. |
| `/v1/user_profiles` and enrollment actions | `user-profiles` | Hosted user management is outside the single-tenant scope. |
| `/v1/sessions/{id}/threads` and its official actions | `threads-and-coordinator` | Session threads are part of the multiagent surface this runtime does not implement; see `contracts/anthropic-cma/threads.md`. |

### Route Coverage Guard

`npm run test:official-routes` extracts routes at test time from the installed,
pinned official SDK's `resources/beta/**/*.js`. Messages, models, and
organization administration are excluded from this managed-agent inventory.
Unrecognized SDK request syntax fails rather than silently losing routes.

Verified on October 8, 2026 with SDK `0.131.0`: 110 distinct method/path pairs.
The split is now 90 resource mounts and 20 explicit refusals — the entire
Work family (data and management planes) is mounted, and `mcp_oauth_validate`
answers a live `initialize` probe, so nothing in the vault or work families
remains a refusal — and no deferred mounts. The
deferral list was tracked in
[issue #706](https://github.com/sandbaseai/sandbase-harness/issues/706) and is
kept as the empty `PENDING_OFFICIAL_ROUTES` array so a future deferral has a
declared home: any entry needs a reason and a follow-up issue link, and stale,
overlapping, or already-mounted deferrals fail the guard. An unlisted missing
route fails with one method/path per line. Route presence is not a claim of
full response-shape, lifecycle, or provider conformance.

## Compatibility Gaps To Track

- Client-side custom tools still need named registration/discovery above the
  event result protocol for the caller-executed path; on self-hosted
  environments a worker already declares tools through `worker poll --tools`
  and the queue carries the call to it.
- Desktop workspace switching still needs a process manager; the CLI registry
  supplies the durable workspace index.
- Additional sandbox provider packages should be separated from the core once
  provider contracts stabilize.
- Historical provider CRUD endpoints, the old `client.modelProviders` SDK
  helper, and the old `managed-agents models ...` CLI command have been
  removed from the v1 public surface. The canonical v1 path is
  `/v1/x/settings`.
- Browser Dashboard smoke tests require an environment that allows binding a
  local HTTP port.
